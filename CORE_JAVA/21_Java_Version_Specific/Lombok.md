# Project Lombok — Interview Notes

> Interview-focused notes covering the Lombok features shown in the video: dependency/plugin setup, `val`, `var`, `@NonNull`, getters/setters, `@ToString`, constructors, `@EqualsAndHashCode`, `@Data`, `@Value`, `@Builder`, and `@Cleanup`.

Lombok reduces Java boilerplate by generating code during compilation. The important interview point is that **Lombok annotations do not magically change Java semantics**; they generate methods/constructors/etc. that the compiler sees.

---

# 1. What is Lombok?

**Project Lombok** is a Java library that uses annotations to reduce repetitive code.

Without Lombok:

```java
class Employee {

    private String name;

    public Employee(String name) {
        this.name = name;
    }

    public String getName() {
        return name;
    }

    public void setName(String name) {
        this.name = name;
    }
}
```

With Lombok:

```java
@Getter
@Setter
class Employee {

    private String name;
}
```

### Interview answer

> Lombok is a Java library that generates boilerplate code such as getters, setters, constructors, `equals()`, `hashCode()`, and `toString()` using annotations.

# 2. Lombok Dependency

For Maven:

```xml
<dependency>
    <groupId>org.projectlombok</groupId>
    <artifactId>lombok</artifactId>
    <version>${lombok.version}</version>
    <scope>provided</scope>
</dependency>
```

For Gradle:

```gradle
dependencies {
    compileOnly("org.projectlombok:lombok:<version>")
    annotationProcessor("org.projectlombok:lombok:<version>")
}
```

### Why `provided` / `compileOnly`?

Lombok generates code during compilation. The generated bytecode contains the methods, so Lombok itself generally does not need to be part of the application's runtime classpath.

> Exact dependency configuration can vary by build tool and project setup.

# 4. `val`

`val` creates a **final local variable** with an inferred type.

```java
val name = "Priyasha";
```

Conceptually:

```java
final String name = "Priyasha";
```

Another example:

```java
val numbers = new ArrayList<Integer>();
```

Conceptually:

```java
final ArrayList<Integer> numbers =
        new ArrayList<Integer>();
```

### Important

`val` means:

```text
Type inference
+
final local variable
```

It does **not** mean the referenced object is immutable.

```java
val list = new ArrayList<String>();

list.add("Java");   // Allowed

// list = new ArrayList<>(); // Not allowed
```

The reference cannot be reassigned, but the object can still be modified.

---

# 5. `var`

`var` creates a local variable whose type is inferred.

```java
var name = "Java";
```

Conceptually:

```java
String name = "Java";
```

Unlike `val`, the variable is **not final**.

```java
var count = 10;

count = 20; // Allowed
```

### `val` vs `var`

| `val` | `var` |
|---|---|
| Type inferred | Type inferred |
| Local variable is final | Variable is mutable/reassignable |
| Reference cannot be reassigned | Reference can be reassigned |
| Lombok feature | Lombok feature |

### Interview one-liner

> `val` is inferred `final`; `var` is inferred but reassignable.

# 6. `@NonNull`

`@NonNull` generates a null check.

```java
public void setName(@NonNull String name) {
    this.name = name;
}
```

Conceptually Lombok generates logic similar to:

```java
if (name == null) {
    throw new NullPointerException("name is marked non-null but is null");
}
```

### Example

```java
class Employee {

    private String name;

    public void setName(@NonNull String name) {
        this.name = name;
    }
}
```

Calling:

```java
employee.setName(null);
```

results in a `NullPointerException`.

### Important

`@NonNull` is **not the same as Optional**.

It does not make a value optional or provide a replacement value.

It expresses:

```text
null is not allowed
```

Lombok can insert null checks in generated constructors, setters, and other relevant generated methods. citeturn0search0turn0search3

# 7. `@Getter` and `@Setter`

## `@Getter`

Generates getter methods.

```java
@Getter
private String name;
```

Equivalent conceptually to:

```java
public String getName() {
    return name;
}
```

For a boolean:

```java
@Getter
private boolean active;
```

the default getter is:

```java
public boolean isActive() {
    return active;
}
```

citeturn0search3

---

## `@Setter`

Generates a setter.

```java
@Setter
private String name;
```

Equivalent to:

```java
public void setName(String name) {
    this.name = name;
}
```

# 8. Class-Level `@Getter` / `@Setter`

Instead of annotating every field:

```java
@Getter
@Setter
class Employee {

    private String name;
    private int age;
}
```

Lombok generates getters/setters for the appropriate fields.

You can also control access:

```java
@Getter(AccessLevel.PRIVATE)
private String salary;
```

### Interview point

`@Getter` and `@Setter` can be placed on:

```text
field
class
```

Field-level configuration can override class-level behavior. citeturn0search3

# 9. `@ToString`

Generates a `toString()` implementation.

```java
@ToString
class Employee {

    private String name;
    private int age;
}
```

Then:

```java
Employee e = new Employee("Priyasha", 25);

System.out.println(e);
```

prints a useful representation instead of:

```text
Employee@5e2de80c
```

### Excluding a field

```java
@ToString
class Employee {

    private String name;

    @ToString.Exclude
    private String password;
}
```

### Interview caution

Do not include sensitive information such as:

```text
password
token
secret
```

in `toString()`.

# 11. `@NoArgsConstructor`

Generates a constructor with no parameters.

```java
@NoArgsConstructor
class Employee {

    private String name;
    private int age;
}
```

Conceptually:

```java
public Employee() {
}
```

---

# 12. `@AllArgsConstructor`

Generates a constructor containing all fields.

```java
@AllArgsConstructor
class Employee {

    private String name;
    private int age;
}
```

Conceptually:

```java
public Employee(String name, int age) {
    this.name = name;
    this.age = age;
}
```

---

# 13. `@RequiredArgsConstructor`

Generates a constructor for:

- `final` fields
- fields marked `@NonNull`

Example:

```java
@RequiredArgsConstructor
class Employee {

    private final int id;

    @NonNull
    private String name;

    private int age;
}
```

Conceptually:

```java
public Employee(int id, String name) {
    this.id = id;
    this.name = name;
}
```

`age` is not included because it is neither `final` nor `@NonNull`.

---

# 14. Constructor Comparison

| Annotation | Generates |
|---|---|
| `@NoArgsConstructor` | No-argument constructor |
| `@RequiredArgsConstructor` | Constructor for `final` and `@NonNull` fields |
| `@AllArgsConstructor` | Constructor containing all fields |

### Interview question

> What does `@RequiredArgsConstructor` include?

**Answer:**

> It includes final fields and fields marked `@NonNull` that require initialization.

---

# 15. `@EqualsAndHashCode`

Generates:

```java
equals()
hashCode()
```

based on relevant fields.

```java
@EqualsAndHashCode
class Employee {

    private int id;
    private String name;
}
```

Conceptually Lombok generates implementations using the class's relevant non-static, non-transient fields by default. citeturn0search2

### Why are they important together?

If:

```java
a.equals(b) == true
```

then:

```java
a.hashCode() == b.hashCode()
```

must also be true.

This is important when using objects in:

```text
HashMap
HashSet
HashTable
```

---

# 16. Excluding Fields

```java
@EqualsAndHashCode
class Employee {

    private int id;
    private String name;

    @EqualsAndHashCode.Exclude
    private String temporaryValue;
}
```

`temporaryValue` is excluded from generated equality/hash-code calculations. citeturn0search2

---

# 17. `callSuper`

If a class extends another class, equality/hash-code handling needs consideration for superclass state.

```java
@EqualsAndHashCode(callSuper = true)
class Manager extends Employee {

    private String department;
}
```

This tells Lombok to include the superclass implementation.

### Interview point

> When a class extends another class, be deliberate about whether superclass fields should participate in equality and hash-code generation.

Lombok warns about this situation because automatically ignoring superclass state can produce incorrect equality semantics. citeturn0search2

# 18. `@Data`

`@Data` is a shortcut annotation.

```java
@Data
class Employee {

    private int id;
    private String name;
}
```

It combines:

```text
@Getter
@Setter
@RequiredArgsConstructor
@ToString
@EqualsAndHashCode
```

citeturn0search1

### Think of it as:

```java
@Data
```

≈

```java
@Getter
@Setter
@RequiredArgsConstructor
@ToString
@EqualsAndHashCode
```

### Important

`@Data` does **not** mean immutable.

Because it generates setters for non-final fields.

---

# 19. `@Data` Example

```java
@Data
class Employee {

    private final int id;

    @NonNull
    private String name;

    private int age;
}
```

Conceptually it provides:

```text
getId()
getName()
getAge()

setName()
setAge()

constructor(id, name)

toString()
equals()
hashCode()
```

The final field `id` does not get a setter.

---

# 20. `@Value`

`@Value` is intended for immutable-style classes.

```java
@Value
class Employee {

    int id;
    String name;
}
```

Conceptually, it combines features for:

```text
final class
private final fields
getters
all-args constructor
toString
equals
hashCode
```

It does not generate setters.

### Example

```java
@Value
class Employee {

    int id;
    String name;
}
```

This is conceptually similar to:

```java
public final class Employee {

    private final int id;
    private final String name;

    public Employee(int id, String name) {
        this.id = id;
        this.name = name;
    }

    public int getId() {
        return id;
    }

    public String getName() {
        return name;
    }
}
```

### Interview point

> `@Value` is Lombok's immutable-value-object shortcut, whereas `@Data` is designed for mutable data objects.

---

# 21. `@Data` vs `@Value`

| `@Data` | `@Value` |
|---|---|
| Mutable by default | Immutable-style |
| Generates setters for non-final fields | No setters |
| Class is not automatically final | Class is final |
| Useful for DTO-style mutable objects | Useful for value objects |
| Getter + Setter | Getter only |

### Easy memory trick

```text
@Data
→ Data object
→ Mutable

@Value
→ Value object
→ Immutable-style
```

# 22. `@Builder`

`@Builder` implements the **Builder Pattern**.

Without Lombok:

```java
Employee employee =
        new Employee(
                101,
                "Priyasha",
                "Java",
                2
        );
```

With many parameters, this becomes hard to read.

With `@Builder`:

```java
Employee employee =
        Employee.builder()
                .id(101)
                .name("Priyasha")
                .technology("Java")
                .experience(2)
                .build();
```

Lombok generates the builder API. citeturn0search5

---

# 23. Why Use Builder?

Builder improves:

### Readability

```java
Employee.builder()
        .name("Priyasha")
        .experience(2)
        .build();
```

is easier to understand than:

```java
new Employee(
        101,
        "Priyasha",
        "Java",
        2
);
```

### Optional fields

You can set only the values you need.

### Avoid constructor parameter confusion

Instead of:

```java
new Employee(101, "Priyasha", 2, "Java");
```

you have:

```java
Employee.builder()
        .id(101)
        .name("Priyasha")
        .experience(2)
        .technology("Java")
        .build();
```

---

# 24. `@Builder` Example

```java
@Builder
class Employee {

    private int id;
    private String name;
    private String technology;
    private int experience;
}
```

Usage:

```java
Employee employee =
        Employee.builder()
                .id(101)
                .name("Priyasha")
                .technology("Java")
                .experience(2)
                .build();
```

Conceptually Lombok creates:

```text
EmployeeBuilder
    ↓
id(...)
name(...)
technology(...)
experience(...)
build()
```

# 25. `@Builder` with `@Singular`

For collections, Lombok supports `@Singular`.

```java
@Builder
class Employee {

    private String name;

    @Singular
    private List<String> skills;
}
```

Usage:

```java
Employee employee =
        Employee.builder()
                .name("Priyasha")
                .skill("Java")
                .skill("Spring")
                .skill("React")
                .build();
```

This is useful when adding individual collection elements through the builder. citeturn0search5

---

# 26. `@Builder` Important Constructor Point

When using:

```java
@Builder
class Employee {
}
```

Lombok generates the builder around a constructor it creates.

If you already have a custom constructor, a safer/clearer approach is often:

```java
@Builder
public Employee(
        int id,
        String name
) {
    this.id = id;
    this.name = name;
}
```

### Interview point

> Be careful when combining `@Builder` with explicit constructors or constructor-generating annotations because the generated constructors can interact.

Lombok's documentation specifically notes that applying `@Builder` to a class is effectively based on an all-arguments constructor, and constructor combinations need to be considered. citeturn0search5

# 27. `@Cleanup`

`@Cleanup` automatically calls `close()` on a resource when the scope is exited.

```java
@Cleanup
InputStream input =
        new FileInputStream("data.txt");
```

Conceptually, Lombok generates cleanup logic similar to:

```java
InputStream input =
        new FileInputStream("data.txt");

try {
    // Use input.
} finally {
    if (input != null) {
        input.close();
    }
}
```

Lombok documents `@Cleanup` as automatic resource management. citeturn0search0turn0search7

---

# 28. `@Cleanup` Example

```java
import lombok.Cleanup;

import java.io.FileInputStream;
import java.io.IOException;

public class CleanupExample {

    public static void main(String[] args)
            throws IOException {

        // Lombok ensures close() is called when this
        // variable goes out of scope.
        @Cleanup
        FileInputStream input =
                new FileInputStream("data.txt");

        int value = input.read();

        System.out.println(value);
    }
}
```

### Interview caution

In modern Java, **try-with-resources is usually preferred** for standard `AutoCloseable` resources because it is built into Java and clearly communicates resource management.

```java
try (FileInputStream input =
        new FileInputStream("data.txt")) {

    int value = input.read();

    System.out.println(value);
}
```

### Interview answer

> `@Cleanup` generates cleanup logic, but for normal `AutoCloseable` resources I would generally prefer Java's try-with-resources because it is standard Java and explicit.

# 29. One Complete Example

```java
import lombok.AllArgsConstructor;
import lombok.Builder;
import lombok.Data;
import lombok.EqualsAndHashCode;
import lombok.Getter;
import lombok.NonNull;
import lombok.Setter;
import lombok.ToString;
import lombok.Value;

import java.util.List;

// Demonstrates @Getter and @Setter.
@Getter
@Setter
class Employee {

    private int id;

    @NonNull
    private String name;

    private String department;
}

// Demonstrates @ToString and @EqualsAndHashCode.
@ToString
@EqualsAndHashCode
class Product {

    private int id;
    private String name;

    // Excluded from generated toString/equals/hashCode.
    @ToString.Exclude
    @EqualsAndHashCode.Exclude
    private String internalCode;
}

// Demonstrates all constructor annotations.
@NoArgsConstructor
@AllArgsConstructor
class Address {

    private String city;
    private String country;
}

// Demonstrates @Data.
@Data
class Customer {

    private final int id;

    @NonNull
    private String name;

    private int age;
}

// Demonstrates @Value.
@Value
class Money {

    int amount;
    String currency;
}

// Demonstrates @Builder.
@Builder
class Order {

    private int id;
    private String customerName;
    private String productName;

    @Builder.Default
    private int quantity = 1;

    @Builder.Default
    private List<String> tags = List.of();
}

public class LombokInterviewDemo {

    public static void main(String[] args) {

        // @Getter / @Setter
        Employee employee = new Employee();

        employee.setId(101);
        employee.setName("Priyasha");
        employee.setDepartment("Engineering");

        System.out.println(employee.getName());

        // @ToString + @EqualsAndHashCode
        Product product = new Product();

        System.out.println(product);

        // @Data
        Customer customer =
                new Customer(1, "Priyasha", 25);

        customer.setAge(26);

        System.out.println(customer);

        // @Value
        Money money =
                new Money(100, "INR");

        System.out.println(money.getAmount());

        // @Builder
        Order order =
                Order.builder()
                        .id(1001)
                        .customerName("Priyasha")
                        .productName("Laptop")
                        .quantity(2)
                        .tag("Electronics")
                        .tag("Office")
                        .build();

        System.out.println(order);
    }
}
```

|---|---|

| `@Setter` | Generates setters |
| `@ToString` | Generates `toString()` |
| `@EqualsAndHashCode` | Generates `equals()` and `hashCode()` |

| `@RequiredArgsConstructor` | Constructor for final / `@NonNull` fields |

# 31. Common Interview Questions

### Q1. What is Lombok?

> A Java library that reduces boilerplate by generating code through annotations.

### Q2. What does `@Data` contain?

> `@Getter`, `@Setter`, `@RequiredArgsConstructor`, `@ToString`, and `@EqualsAndHashCode`.

### Q3. Is `@Data` immutable?

> No. It generates setters for non-final fields.

### Q4. Is `@Value` immutable?

> It is designed for immutable-style value objects: the class is final, fields are private/final, and setters are not generated. The referenced objects themselves can still be mutable, so deep immutability is not guaranteed.

### Q5. What does `@RequiredArgsConstructor` include?

> Final fields and fields marked `@NonNull`.

### Q6. Difference between `@Data` and `@Value`?

> `@Data` is mutable by default; `@Value` is immutable-style and does not generate setters.

### Q7. What does `@Builder` solve?

> It provides a readable way to construct objects, especially when there are many optional parameters.

### Q8. What does `@NonNull` do?

> Lombok generates a null check and throws `NullPointerException` when the annotated value is null.

### Q9. Why are `equals()` and `hashCode()` generated together?

> Because they must follow the Java equality/hash-code contract, especially when objects are used in hash-based collections.

### Q10. What does `@Cleanup` do?

> It generates cleanup logic that calls the resource's `close()` method when leaving scope.

### Q11. `val` vs `var`?

> Both infer the local variable type; `val` makes the local variable final, while `var` allows reassignment.

### Q12. Is Lombok runtime magic?

> No. Lombok is primarily a compile-time code-generation tool using annotation processing.

# 32. Important Interview Cautions

## 1. Lombok can hide generated code

When debugging or reviewing code, know what annotations generate.

For example:

```java
@Data
class Employee {
}
```

is not "just one annotation"; it represents several generated behaviors.

---

## 2. Be careful with `@Data` on JPA entities

`@Data` automatically generates:

```text
equals()
hashCode()
toString()
```

For ORM entities, these methods can require careful design because entity identity, lazy relationships, and mutable state can make generated equality/string representations problematic.

---

## 3. Be careful with `@ToString`

Do not accidentally expose:

```text
password
access token
secret
large object graph
```

---

## 4. Be careful with `@EqualsAndHashCode`

Mutable fields used in `hashCode()` can cause problems if an object is modified after being placed into a `HashSet` or used as a `HashMap` key.

---

## 5. `@Cleanup` vs try-with-resources

For normal `AutoCloseable` resources:

```java
try (...) {
}
```

is generally the clearer standard-Java choice.

# 34. Strong Interview Summary

> **Lombok is a compile-time code-generation library used to reduce Java boilerplate. The most common annotations are `@Getter`, `@Setter`, `@Data`, `@Value`, constructor annotations, `@EqualsAndHashCode`, `@Builder`, `@NonNull`, and `@Cleanup`. `@Data` is mainly for convenient mutable data objects, while `@Value` is for immutable-style value objects. `@Builder` improves object construction readability, and `@NonNull` generates null checks.**
